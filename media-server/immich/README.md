# Immich for Kubarr

Photo and video backup at `http://immich:2283` inside the `immich` namespace (Kubarr's gateway discovers the `immich` Service). This chart deploys the v3.2.2 server and matching CPU machine-learning image, the upstream v3.2.2 compose PostgreSQL 14 image with VectorChord 0.4.3 / pgvectors 0.2.0, and Valkey 9. The database and Valkey images are pinned to the digests in the [v3.2.2 compose file](https://raw.githubusercontent.com/immich-app/immich/v3.2.2/docker/docker-compose.yml). Upgrade the server and ML tags together, checking [upstream upgrade notes](https://docs.immich.app/install/upgrading/) and the corresponding compose database image first.

## Before installation

1. Allocate at least **2 CPU cores and 6 GiB RAM** to Immich (4 cores and 8 GiB recommended). The ML image on amd64 requires **x86-64-v2**. Prepare writable, persistent shared media storage (`media-data` in namespace `immich`, using Kubarr managed NFS by default). The `/data` upload root uses the `immich` subdirectory. The NFS export must permit UID/GID 1000 to write; pre-create `immich` with appropriate ownership/permissions if your NFS server root-squashes or denies subPath creation. Avoid modifying Immich's library folders outside the app.
2. **PostgreSQL must have local, Unix-compatible block storage, preferably SSD.** By default the claim uses the cluster's default StorageClass (which need not be named `local-path`). Verify it provides local/block storage; otherwise set `database.bundled.persistence.storageClassName` to a *local block* class or supply `database.bundled.persistence.existingClaim` backed by local storage. Never use `media-data`, NFS, SMB or any network share for the database. RWO alone does not imply local storage. On HDD set `database.bundled.storageType=HDD`. A local PVC pins the database to its node; plan node recovery and backups accordingly. The chart retains StatefulSet PVCs on uninstall.
3. No database Secret needs to be pre-created for bundled PostgreSQL. Install through Kubarr or directly with Helm:

   ```sh
    helm dependency build --skip-refresh media-server/immich
    helm upgrade --install immich media-server/immich -n immich --create-namespace
   ```

    Helm generates a 64-character random password in `immich-db` (`DB_PASSWORD`) and keeps the Secret after uninstall. Back it up securely, for example export `kubectl -n immich get secret immich-db -o yaml` directly into an encrypted backup or secret manager, not a public log or repository. Upgrades look up and reuse the live password, failing if the Secret is missing; reinstall against a retained database claim also fails without it. Restore the original Secret first. Changing the Secret alone will **not** change the password in an initialized Postgres database. Set `database.existingSecret` / `database.passwordKey` to use your own Secret (no generation). The server and database reference the same key. Ensure media permissions and local storage are suitable before installation.

The ML model cache uses the managed NFS media claim's private `media-server/immich/immich/models` subdirectory (the middle component is the Helm fullname). A root init container creates/chowns it for UID/GID 1000 on Kubarr's export; on a root-squashed external export preprovision it on the server. Set `machineLearning.cache.storageClassName` for a dedicated claim or `machineLearning.cache.existingClaim` for an existing one. An old `immich-ml` PVC is not automatically copied: back it up and migrate it, or discard this **regenerable cache**, then set `storage.migrationConfirmed=true` on upgrade. Immich PostgreSQL **must remain on local/block storage**: [upstream explicitly says never to put its database on a network share](https://docs.immich.app/install/requirements/). The bundled Valkey holds an ephemeral cache. Tune resource requests for your node capacity. Disable `machineLearning.enabled` only if ML features are not required (turn off ML jobs in Immich settings).

## External dependencies

For an external DB set `database.bundled.enabled=false`, `database.host`, `database.port`, `database.username`, `database.name` and `database.existingSecret`. The DB must run a PostgreSQL version and vector extension supported by your Immich release; see [upstream standalone database guidance](https://docs.immich.app/administration/postgres-standalone/). For external Redis/Valkey set `cache.bundled.enabled=false`, `cache.host`, `cache.port`, and optionally `cache.existingSecret` (key `REDIS_PASSWORD`). Bundled Valkey has no password and is cluster-internal; do not expose it publicly. `networkPolicy.egressTo` can allow additional namespaces for external services; for private IPs outside allowed namespace selectors, supply suitable NetworkPolicies in the cluster. The internal policy permits traffic between the chart's pods, and the shared Kubarr policy permits gateway ingress, DNS and public egress.

## Backup and limitations

Back up **both** the database (Immich's built-in SQL dumps under `/data/backups`, or `pg_dump` with external retention) and the entire `/data` media tree, especially `upload`, `library` and `profile`. Preserve the database password and settings too. Restore the assets and matching SQL dump together; if live backups cannot be stopped, [back up the database before the filesystem](https://docs.immich.app/administration/backup-and-restore/). PostgreSQL's PVC snapshot alone is not a replacement for tested logical backups. Existing library assets are not automatically indexed merely by mounting them; use Immich's external-library workflow if applicable. No ingress/TLS or transcoding/ML hardware acceleration is provisioned; configure HTTPS on the Kubarr gateway for remote mobile uploads.
